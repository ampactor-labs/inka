# Per-Domain SOTA


## Effects & negation — algebraic effects/handlers, effect rows (Koka), capabilities (Effekt), modal effect types (Tang–Lindley), and the near-unique power of proving the NEGATIVE (transitive !E)

**SOTA systems**
- Koka — Daan Leijen (Microsoft Research), 2014→2025 (v3.1.x, ICFP'25 lazy constructors) — row-polymorphic effect types with SCOPED/DUPLICATE labels, full Hindley-Milner inference of effects, efficient handler compilation via evidence-passing + named handlers, Perceus reference counting. LIMIT: rows leak through higher-order functions (an effect variable must be threaded on every arrow; encapsulation/parametricity is not guaranteed — PLAN.md's 'textbook failure mode'). Crucially, Koka has NO native Boolean negation — it adopted scoped duplicate-labeled rows *specifically to avoid* lacks/absence constraints, so 'prove effect E is ABSENT transitively' is not expressible.
- Effekt — Brachthäuser, Schuster, Ostermann; OOPSLA 2020 'Effects as Capabilities' + OOPSLA 2022 'Effects, capabilities, and boxes' — contextual/capability-passing effects: a computation's type lists the capabilities it requires from context; functions are SECOND-CLASS (block parameters) so the higher-order leak literally CANNOT occur and no effect variables are needed; boxing lifts a second-class block to a first-class value at the cost of tracking degree-of-impurity. LIMIT: second-class means effects cannot freely ESCAPE (you cannot return a handler-using closure without boxing); no native negation; their own admission that this 'impedes reasoning about purity'; boxing reintroduces the tracking it set out to remove.
- Modal Effect Types — Wenhao Tang, Sam Lindley, Daniel Hillerström et al.; POPL 2025 (arXiv 2407.11816, PACMPL Vol.9 POPL Art. — doi 10.1145/3720476) — DECOUPLES effect tracking from the function arrow via two MODALITIES: an absolute modality that sets the ambient effect context and a relative modality that extends it; a box modality lets effect-polymorphic code be written WITHOUT effect variables, re-admitting first-class escape under proof. Solves the leak + encapsulation while keeping rows' expressiveness. LIMIT: research calculus (no shipping language, no runtime substrate); modality annotations are a new surface burden; NO negation primitive; the continuation carries no effect-world (no cross-context-resume typing).
- Rows and Capabilities as Modal Effects — Tang & Lindley; POPL 2026 (arXiv 2507.10301, PACMPL Vol.10 POPL Art. 32, Jan 2026; HOPE 2025 extended abstract) — THE convergence theorem: row-based AND capability-based effect systems are both MACRO-ENCODABLE into one modal framework, with encodings proven to preserve types and semantics. This is precisely the rows-vs-capabilities unification PLAN.md §4③ names as the defining open question — now answered in the published literature. LIMIT: it unifies rows + capabilities but still has NO Boolean negation; it is an encoding/comparison framework, not an implemented medium; the modality is the *route*, with no first-class-continuation effect-world and no runtime/memory substrate.
- OCaml 5 effect handlers — Sivaramakrishnan, Dolan, White, Madhavapeddy et al., 2021–2022 — first MAINSTREAM language shipping runtime effect handlers (schedulers, async, generators) with one-shot continuations. LIMIT: effects are UNTYPED — invisible in the type, no effect row at all, therefore zero static negation/absence. The continuation-without-the-type (the language-level analog of Temporal's gap).
- WasmFX / typed continuations for WebAssembly — Phipps-Costin, Rossberg, Lindley et al., 2023–2025 — a low-level typed-continuation / effect-handler primitive for the WASM substrate. LIMIT: a control primitive with no effect row and no negation — exactly the substrate Mentl's `lower` must project onto; relevant as the continuation-reification target, not as a type system.
- Frank / Links — Lindley, McBride, Hillerström — Frank's 'do-be-do' ability tracking and Links's row-based effects for the web; the academic lineage rows-with-handlers descends from. Subsumed by the modal line above but the source of the 'effects as an ability the context must discharge' framing.

**Key ideas:** Algebraic effects separate an operation's SYNTAX (perform) from its INTERPRETATION (handler); a handler is a delimited-control catcher with typed resume cardinality (one-shot vs multi-shot). The whole field's central tension is that effect tracking is ENTANGLED with the function arrow, and there are only two classical escapes, each lossy: (1) ROWS (Koka/Links) thread an effect-set with a tail variable through every arrow — expressive and HM-inferable, but the variable LEAKS through higher-order functions (encapsulation fails); (2) CAPABILITIES (Effekt) make functions second-class so no variable is needed and the leak cannot occur — but then effects cannot ESCAPE (no first-class handler-closures without boxing). MODALITIES (Tang–Lindley) are the third escape: track effects on the AMBIENT CONTEXT via an absolute/relative modality pair instead of on the arrow, so polymorphism needs no effect variable and escape is re-admitted under proof — and POPL 2026 shows rows and capabilities are both just encodings into this one modal frame. Orthogonal to all of this is NEGATION/ABSENCE: classical presence-absence polymorphism (Rémy-style rows, Lindley 'lacks' predicates) expresses absence as a CONSTRAINT, never a first-class Boolean; essentially no shipping system has transitive `!E` ('this code provably never performs E, through the whole call graph'). That negative is the existential question for autonomous machine-generated code (prove it won't exfiltrate / allocate / reach the network), and it is the arm every leader skipped.

**Frontier:** The single open problem: can capabilities' no-leak threading coexist with rows' BOOLEAN negation, sound simultaneously under (a) polymorphism AND (b) first-class / multi-shot continuations? Modal effect types resolved the rows-vs-capabilities half (POPL 2025) and proved the unification (POPL 2026) — but left negation entirely untouched, and no modal/row/capability system types what happens when a CONTINUATION crosses an effect-world boundary (persisted, then resumed under a different handler-set, or across a recompile). So two frontiers remain genuinely unsolved anywhere: (1) sound transitive `!E` under polymorphism — the very reason Koka omits negation is that an open row variable can be instantiated to re-admit the forbidden effect; (2) lifting `!E` to the TIME axis — carrying the effect-world on the continuation so a cross-context resume is a static error. These are exactly the two Mentl-frontier items, and they are where the published field has nothing.

## Ownership, borrowing, value semantics, linear/affine/graded types, region types, and unboxed/columnar value representation — the "memory discipline" arm: who may touch a value, when it dies, and how wide its bits are. **Key ideas:** The field is organized around four originally-separate disciplines that are slowly collapsing into one. (1) LINEARITY/AFFINITY — a value used exactly (≤) once; Rust's move, Linear Haskell's %1, Austral's linear types. (2) BORROWING — temporary non-consuming access, the escape valve so you needn't thread values everywhere; Rust's &/&mut, Hylo's inout/let, regions/lifetimes scoping how long a borrow is valid. (3) VALUE SEMANTICS — independence: a value has no observable aliases, so local reasoning holds (Hylo). (4) GRADED/QUANTITATIVE generalization — Granule's insight that linearity is just the 0/1/ω semiring, and ANY semiring (security lattice, sensitivity, fractions) grades a modality; fractional uniqueness then shows uniqueness and borrowing are two readings of one fractional-permission algebra (whole = unique/mutable, fractions = shared/read). Orthogonal but inseparable is REPRESENTATION: Arrow/Polars/DuckDB prove unboxed columnar (one sequence kind, element type drives layout) beats boxed-everything; the representation gradient (i32 floor → i64/f64/f32/v128/v128-lanes as cash-outs of the inferred type) is the value-layer dual of the ownership gradient. The deepest unifying observation, which no shipped system holds: ownership IS information about USE that the program graph already contains (use-count, last-use, aliasing), so it should be DERIVED and projected, never authored — and it is the same kind of fact as an effect (a constraint on what crossing an edge requires/forbids), which is why Mentl folds 'own performs Consume' / 'ref is !Mutate' into the one Boolean effect row.

Three converging fronts: (a) Hylo's value-semantics route (no lifetime annotations) versus its own confession that 'moves metastasize' — can you keep moves AND make borrows invisible? The unclaimed summit, which is exactly Mentl's bet: treat ownership as a PROJECTION of the use-graph (use-count 0/1/2+ → Inferred/Own/Ref) inside the SAME Boolean effect row that already carries !Alloc/!IO, so 'prove this value is never aliased across this thread boundary' is the same kind of theorem as 'prove this region performs no allocation' — negation included. No production system unifies ownership, effects, and a memcpy-serializable representation; that conjunction is the body none of the tentacles grew.

**Where they stop:** Rust: ownership is real and zero-cost but ANNOTATED (lifetimes viral) and quarantined from the type/effect row — a borrow checker bolted beside HM, not one read of one graph; it cannot say '!E' or prove absence, and 2025's Polonius/Tree-Borrows effort is spent re-accepting programs it should never have rejected. Hylo: removed lifetime annotations but proved its own ceiling — 'moves metastasize, you can't escape borrows, only escape annotating them' — and bought independence by forbidding aliasing, the opposite of Mentl's one shared graph; conventions are still author-chosen and there is no effect algebra. Austral/Linear Haskell: have linearity but ZERO inference (or linearity-in-the-arrow), so the developer thinks about ownership constantly — they fail the Hylo-quiet bar by construction. Granule: has the exact algebra (graded modalities, fractional uniqueness) Mentl wants but no substrate, no codegen, no representation gradient, and grades stay annotated — a proof-of-concept tentacle with no body. Mojo: infers DEATH (ASAP) but not the passing convention, and never connects ownership to an effect row or to proof-of-absence. Vale/Pony: fall back to runtime generation checks, or expose six viral capabilities with no Boolean algebra/negation/inference. Arrow/Polars/DuckDB: nailed unboxed columnar representation ('one sequence type, many element types') but only as a DATA library — no ownership, no effects, no types-as-proof, no continuation. Each holds exactly one of {inference, the algebra, the representation, the row, proof-of-absence} and lacks the rest.

**Mentl's arm:** Mentl's ownership arm (§4⑤, interrogation #5) makes ownership the FIFTH aspect of the one cursor-read, not a separate checker: own performs the Consume effect, ref is a row constraint (!Mutate), and the marker is INFERRED from use-count (0/1/2+ → Inferred/Own/Ref), held explicitly to the Hylo-quiet bar — 'if the developer has to think about it, the inference failed.' ## Refinement types, SMT-backed verification, gradual/residual verification, and the dependent-types frontier — the arm Mentl surfaces as refinement types + the Verify effect (default V_Pending ledger discharged by an SMT handler-swap, "same source, deeper proof engine"), with predicates carried as refined Exprs in the one graph (predicate-is-Expr, no parallel PExpr) and per-program-point narrowing as a cursor read.

**SOTA systems**
- Liquid Haskell — Vazou/Jhala/Rondon/Kawaguchi, 2014→2025 (SPLASH/POPL line) — refinement types over GHC; reduces type-checking to SMT-decidable (QF-UFLIA) Horn-constraint solving via Z3, fully automatic, zero runtime overhead; extended to refinement reflection + PLE for hand-checked equational proofs-in-Haskell. LIMIT: refinements live in a SEPARATE predicate DSL ({v:Int | p}) bolted onto an unrefined host with no effect system; restricted to the decidable fragment; higher-order/modular abstraction was a gap until 2025; whole-function re-verification, no principled proof reuse; SMT brittleness (proofs break on unrelated edits).
- Flux: Liquid Types for Rust — Lehmann/Jhala et al., PLDI/PACMPL 2023 — liquid refinements that compose with Rust ownership/borrowing to index mutable locations with pure values and do strong updates SMT-decidably; ergonomic type-based verification of pointer code. LIMIT: bolted onto Rust; decidable-fragment-only; no effect row, no continuation/durability axis; refinement surface is still a separate annotation language, not the program's own graph.
- Generic Refinement Types — Lehmann/Kurashige/Akiti/Krishnakumar/Jhala, POPL 2025 — modular HIGHER-ORDER refinements that abstract invariants over function contracts and Rust traits while staying SMT-decidable; closes Liquid types' long-standing higher-order modularity gap. LIMIT: still a refinement-annotation layer over a host language; no integration with an effect/capability row; abstraction is over contracts, not over a unified effect+ownership+refinement read.
- F* + Pulse/PulseCore/Steel — Swamy/Martínez/Rastogi/Ebner et al., 2016→PLDI 2025 (PulseCore) — the closest thing to a 'body': dependent types subsuming refinements, an SMT backend (Z3) for automatic discharge, user tactics (Meta-F*), a real layered EFFECT system (DM4Free), and concurrent separation logic (Steel/Pulse) for stateful/concurrent proofs; extracts to OCaml/C/Wasm (Project Everest: verified HACL*/EverParse shipped). - Dafny — Leino, 2010→present (Microsoft) — auto-active verification: SMT (Z3) discharges pre/post/invariants for imperative code with high automation; the accessibility benchmark for non-experts. LIMIT: binary verify/fail with no principled residual (its {:axiom}/assume escape hatches are UNSOUND holes, not tracked debt); notorious SMT instability/flakiness (nondeterministic timeouts on unrelated edits); no effect row, no ownership, no refinement-as-program-expression.
- Verus — Lattuada/Hance/Parno et al., OOPSLA 2023 (+VerusBelt 2026) — verifies Rust via LINEAR GHOST TYPES (separation-logic-style resource permissions encoded in Rust's own linear type system) + SMT; strong memory/concurrency proofs reusing the borrow checker. LIMIT: manual ghost-proof authoring, same SMT brittleness, decidable-fragment; no gradual residual; no continuation/durability or carried-Reason layer.
- Gradual refinement types / Gradual Liquid Type Inference — Lehmann & Tanter, POPL 2017; Vazou/Tanter, ICFP 2018 — THE direct ancestor of Mentl's Verify-ledger: imprecise refinements (?) with sound static→dynamic casting; gradual liquid inference migrates programs by inserting runtime checks where static proof is incomplete. LIMIT: research prototype; the static/dynamic boundary is TYPE-driven cast insertion, not a handler swap; no effect-row integration, no graph, no proof reuse across the gradient.
- Sound Gradual Verification / Gradual C0 — Wise/Zimmerman/Aldrich/Bader, OOPSLA 2020→TOPLAS 2025 — first SOUND gradual verification for recursive heap structures via symbolic execution over implicit dynamic frames; partial specs verified by static+dynamic checks with optimized runtime-check generation; the residual-verification frontier. LIMIT: verification is MANUAL (tactics), undecidable, expressiveness bought at the cost of automation; proof-assistant-first, PL-ergonomics/runtime secondary; no automatic refinement discharge by default.

**Key ideas:** The field's spine: lift a logical predicate over a value (a REFINEMENT {v:T | p(v)}) and discharge proof obligations automatically by compiling them to an SMT solver (Z3/CVC5) over a DECIDABLE fragment (QF-UFLIA + arrays/datatypes). Subtyping becomes implication-checking; verification becomes constraint-solving. Three escalating power tiers, each trading automation for expressiveness: (1) liquid/refinement types — decidable, fully automatic, the sweet spot (LH, Flux, Verus, Dafny); (2) dependent types — unbounded expressiveness, manual tactic proofs, undecidable (Lean, Idris, F*); (3) gradual/residual verification — partial specs, sound static+dynamic split, the bridge between checked and unchecked code (Lehmann-Tanter, Gradual C0). Cross-cutting ideas: flow-sensitive/path-sensitive narrowing (a value's refinement tightens per program point via if/match/assert — occurrence typing); refinement reflection (lift functions into the logic for equational proofs); proof-carrying code (Necula — the proof travels with the binary, independently checkable); separation logic / linear ghost permissions for heap+concurrency (Steel, Verus); and the 2024-2026 surge of LLM-assisted proof synthesis (AutoVerus, Goedel-Prover, vericoding) treating the verifier as an oracle a model proposes against — structurally exactly Mentl's 'any intelligence proposes, the kernel disposes.'

**Frontier:** Five live frontiers, all 2024-2026: (1) PROOF ROBUSTNESS/STABILITY — SMT brittleness is the field's open wound: proofs time out or break nondeterministically on edits unrelated to the property; nobody has a principled fix, only triggers/fuel heuristics. (2) PROOF REUSE & INCREMENTALITY — nearly every tool re-verifies a whole function on any change; incremental/compositional re-verification at the obligation granularity is largely unsolved. (3) SOUND GRADUAL/RESIDUAL VERIFICATION — only put on sound footing in 2024 (Zimmerman, symbolic execution over IDF); how to carry undischarged obligations as principled DEBT (runtime check or tracked pending) rather than unsound assume, and how the static→dynamic boundary composes, is the active edge. (4) MODULAR/HIGHER-ORDER refinement — Generic Refinement Types (POPL 2025) just opened abstracting refinements over function contracts/traits SMT-decidably; composing refinement with effects/capabilities is untouched. (5) MACHINE-PROPOSED PROOF — LLM agents (AutoVerus >90% on benchmarks, Goedel-Prover, vericoding) racing to author proofs against the verifier-as-oracle; this is the field unknowingly building Mentl's proposer/kernel split.

**Where they stop:** Every leader stops at the SAME structural seam: the refinement predicate is a SEPARATE logic surface bolted onto an unrefined host. Liquid Haskell's {v:Int | p}, F*'s logical formulas, Dafny's spec language, Flux/Verus's annotation DSL — all maintain a PARALLEL predicate language distinct from the program's own expression graph (Mentl's predicate-is-Expr / PExpr-elimination names exactly this Carried-Truth violation: the predicate IS an Expr the graph already holds, re-derived into a second ADT). Fifth: the deepest leaders (Lean/Idris/F*) make the developer WRITE THE PROOF by hand (proof-oriented programming) — the proof burden is the tentacle-without-the-body: maximal power, zero quietness, no medium for the ordinary developer. They have the proof engine; none have it as ONE arm of a single cursor read over a unified graph with inferred ownership, an effect row, a Reason chain, and a gradual default that costs nothing until you ask.

LIMIT: graded-modal calculus; a separate grade algebra (not the same Boolean row that proves !Alloc); research language, no negation, no continuation/TIME story.

LIMIT: a calculus/theory, not a production medium — no unification with allocation/IO effects in one negation-bearing algebra, no backend, no TIME/continuation axis.
- FIDES — 'Securing AI Agents with Information-Flow Control' — Costa, Köpf, Russinovich, Abdelnabi, Paverd et al. (Microsoft, 2025); + 'Towards Verifiably Safe Tool Use for LLM Agents' (arXiv 2601.08012, 2026); AgentGuardian (2601.10440) — the FRONTIER application: dynamic taint-tracking over an LLM agent's messages/tool-args/results on a PRODUCT lattice (confidentiality × integrity × type); a policy engine gates 'consequential actions' until labels are verified; proves 'explicit secrecy'. LIMIT: DYNAMIC enforcement (runtime taint, not a compile-time theorem); explicit secrecy is WEAKER than non-interference — it does NOT catch implicit flows through adversary-visible control decisions; the policy engine is a system EXTERNAL to the language type system (policing, not a medium); enforcement reduces task-completion (friction, not transparency).

**Key ideas:** A security LATTICE ℒ (meet=public, join=secret) labels every value; NON-INTERFERENCE is the gold property: no change to a Secret input may, by ANY path, alter a Public-observable output. Flows split into EXPLICIT (x := secret) and the hard IMPLICIT (if secret then a else b — the branch condition leaks via a program-counter/pc label that must taint everything in its scope), plus termination/timing/progress side-channels. DCC's insight: non-interference IS a dependency/protection monad — one lattice-indexed modality subsumes IFC, slicing, binding-time. The field's two enforcement poles: STATIC (Jif/FlowCaml/DCC/structural — prove ahead, but historically annotation-heavy → unadopted) vs DYNAMIC (LIO/Jeeves/FIDES — float labels at runtime, flexible but only halts at the leak). Declassification is the necessary escape valve (no real program is purely non-interferent — you must release a hashed password); the discipline (Sabelfeld & Sands, 'Declassification: Dimensions and Principles') names WHAT/WHO/WHERE/WHEN and ROBUST declassification (an attacker can't abuse the release). Capability/ocap security is the ORTHOGONAL axis: it bounds AUTHORITY (who can reach an object) but not FLOW (where the data goes after). Modern direction (graded coeffects, structural/modal IFC, session-typed regrading): flow as a MODALITY/grade in the type system; and the explosive 2025-2026 frontier: IFC as the leading defense for LLM agents, where instructions and data are the same text and prompt-injection IS an integrity-flow violation.

**Frontier:** Four unsolved problems define the edge. (1) ADOPTABILITY — IFC has been theoretically 'the holy grail' for 25 years yet barely adopted because specifications 'spiral out of control'; the open problem is making flow labels INFERRED and quiet enough that the developer never writes them (FlowCaml proved inference is possible; nobody has made it quiet AND integrated). (2) UNIFICATION — every system keeps flow in a SEPARATE lattice/type-system/runtime from effects, ownership, and capability; nobody has put confidentiality-flow in the SAME Boolean algebra (with NEGATION) that proves !Alloc/!IO, so non-interference can be proven transitively the way absence-of-allocation is. (3) IMPLICIT + side-channel soundness — explicit flows are easy; sound, non-conservative handling of implicit (pc-label), termination, progress, and timing channels under declassification remains hard (FIDES explicitly punts implicit control-flow flows; Nonmalleable Progress Leakage, 2505.12210, is live work). (4) THE AGENTIC + TIME axes — proving non-interference for autonomous, tool-using AI agents (FIDES/2026) where data=instructions, AND lifting a flow label across a PERSISTED continuation (a secret captured in a resumable computation resumed in a new handler world). Plus principled+inferred ROBUST declassification, and a confidentiality⊗integrity product lattice in one algebra.

**Where they stop:** Each leader built one face of the IFC arm and stopped where it lacked the others. Jif: full DLM labels but EXPLICIT and Java-bolted — the annotation burden that killed adoption; no inference, no unification. FlowCaml: got INFERENCE right but as a disjoint security type system with no negation and no production reach. DCC: the perfect non-interference THEOREM (a protection monad) but only a core calculus — no effects, ownership, surface, or backend. LIO/Jeeves/FIDES: flexible but DYNAMIC — they police at runtime, the inverse of 'nothing executes unproven', and FIDES's 'explicit secrecy' can't even see implicit flows. Storm/Granule: closest (refinement/graded-modal labels) but domain-specific or in a SEPARATE grade algebra without Boolean negation. Capability security (E/Pony/seL4/Wasm): proves AUTHORITY but not FLOW — an authorized read can still leak to a log; seL4 is proven BY HAND, not inferred; Pony's rcaps are the ownership arm, not confidentiality. Structural/modal IFC (Gouni-Pfenning-Aldrich 2025): the deepest theory but a calculus, not a medium. The universal tentacle-without-body: IFC always lives in its OWN lattice/system/runtime — explicit (unadopted) OR dynamic (unproven) OR pure-calculus (no medium) — and NONE place flow in the same negation-bearing, INFERRED, cursor-projected effect row that already proves !Alloc.

**Mentl's arm:** Mentl's §4⑥ arm IS the body these tentacles reached toward: flow is NOT a separate subsystem — PFlowLe(src,dst) is folded into the Predicate ADT (src/types.mn:992), so a flow obligation is discharged by the SAME Verify machinery as a refinement (verify(span, PFlowLe(src,dst), reason) IS the ifc_check — the scaffold already deletes any standalone ifc_check subsystem). The FlowLabel lattice (Public ⊑ Tainted ⊑ Secret, flow_join/flow_le in types.mn) rides ALONGSIDE the Ty and EffRow on every node; the EfNeg in a function's row IS the non-interference proof (query.mn row_flow_label: !Log on a Secret-carrying row proves the data cannot reach Log — exactly !Alloc's transitive proof, now for flow). QFlowOf (query.mn) PROJECTS the label the graph already holds (reading TRefined/TName/EfNeg) — never a second ledger: Carried-Truth at the IFC layer. This converges every tentacle at once: (a) it gets FlowCaml's inference but in the unified HM walk, not a disjoint system; (b) it realizes DCC's protection-monad theorem as a lattice-indexed Predicate over the real graph; (c) it is STATIC and ahead-of-execution (Mentl's §0 'nothing executes unproven'), surpassing LIO/FIDES's dynamic policing; (d) ocap/capability security is SUBSUMED — the ~> handler chain IS the capability stack ('proven not audited', §4⑥: !E + the ~> trust hierarchy already give authority-bounding, and IFC adds the flow axis ocap structurally cannot express); (e) declassification is Tainted→Public discharged by the verify_smt handler swap (provable non-invertibility), same source, deeper engine. The medium-level move no prior system made: confidentiality-flow, capability-authority, effect-presence, and absence-proof become FOUR projections of one Boolean-row read, inferred and cursor-projected, so a `"{secret}" ~> Log` is E_IFCFlowViolation at compile time with a walkable Reason — the spec never spirals because the developer writes labels only at intent boundaries and Public is the silent default.

**Absorb:**

This is the load-bearing design constraint, not a nicety — it is WHY every prior IFC language died.

## Graph-as-program / incremental computation / e-graphs & equality saturation / Datalog & differential dataflow — the "one graph, two operations (draw-edge, project)" substrate and its demand-driven, equality-saturating, incrementally-maintained projections.

**SOTA systems**
- egg — Willsey, Nandi, Wang, Flatt, Tatlock, Panchekha (POPL 2021, distinguished paper) — a fast, extensible Rust e-graph library that made equality saturation practical: deferred/rebuild-based congruence invariant restoration (amortizing the union-find + congruence-closure maintenance) + e-class analyses (a semilattice value per e-class, e.g. constant-fold, interval, free-vars). Powers Herbie (float accuracy), Ruler (rule synthesis), szalinski, Tensat. LIMIT: rewrites are SYNTACTIC — no notion of effects/observability, so it can only equate values, never reason about what RUNS; extraction is a separate, NP-hard post-pass bolted onto the saturated graph.
- egglog — Zhang, Wang, Willsey, Sundararaman, Panchekha, Tatlock et al., 'Better Together: Unifying Datalog and Equality Saturation' (PLDI 2023, distinguished paper) — the current SOTA: e-graphs ARE a Datalog database whose relations are kept congruent; gives incremental (seminaive) rule evaluation, lattice/semilattice merge functions for analyses, and unifies rewriting + program analysis in one fixpoint engine. Adopted now over egg for tensor/ML reasoning (sharding, layout). LIMIT: still value-equality only — no effect-aware/observational gating; extraction remains NP-hard and external; the database is a SIDE structure, not the program's own AST graph.
- Relational e-matching — Zhang, Wang, Willsey, Tatlock (POPL 2022) — recast e-matching (the e-graph pattern-search bottleneck) as a worst-case-optimal relational join (generic join / Free Join), turning the matching engine into a database query — the bridge that made egglog possible. LIMIT: an engineering substrate for matching, not a semantics for effects or incrementality of the surrounding compiler.
- salsa / rustc query system / rust-analyzer — Niko Matsakis, Jonathan Turner, Aleksey Kladov et al. (2018–2026, salsa 3.0 era) — demand-driven, memoized, 'red/green' incremental recomputation: a compiler as a set of pure queries K→V over tracked inputs; durable incrementality persists the dependency graph across sessions. The dominant industrial model for incremental IDE compilation. LIMIT: queries are COARSE black-box functions over an external dep-graph; the program AST is data PASSED THROUGH queries, not itself the incremental graph — invalidation is key-granular, not edge-granular, and the dep-graph is a second structure maintained alongside the program.
- Adapton / self-adjusting computation — Matthew Hammer, Umut Acar et al. (Adapton PLDI 2014; SAC, Acar's thesis 2005, 'A Library for Self-Adjusting Computation' Acar–Blume–Harper–Tangwongsan) — demand-driven incremental computation with a dynamic dependency graph (DDG) of thunks + change-propagation; the theoretical root of demand-driven IC, with from-scratch optimality results. LIMIT: a general-purpose IC LIBRARY with manual modifiable-ref placement; no equality reasoning, no types, no effects — incrementality without the rest of the body.
- Differential Dataflow / Timely Dataflow / DBSP / Materialize — Frank McSherry, Derek Murray, Michael Isard (Naiad SOSP 2013; Differential Dataflow CIDR 2013); DBSP — Budiu, McSherry, Ryzhyk, Tannen (VLDB 2023, 'Automatic IVM for Rich Query Languages', VLDB Journal 2025) — datasets as streams of (data, time, multiplicity) differences; arbitrary (recursive) dataflows maintained incrementally under input deltas with strict consistency; DBSP gives a clean circuit algebra (Z-sets + the differentiation/integration operators) that compiles ANY query to its incremental version mechanically. Materialize productionizes it as streaming SQL. LIMIT: a DATA-relational engine — maintains query RESULTS over changing tuples; it is not a program representation, has no rewriting/equality, no types, no effects.
- Cranelift aegraphs (acyclic e-graphs) — Chris Fallin (2023) — equality saturation folded directly into a production compiler's mid-end IR: an e-graph fused with the SSA value graph so rewriting and code-selection share one structure, with an acyclic discipline + eager rewriting to bound cost. The closest industrial move toward 'the IR IS the e-graph'. LIMIT: still value-level optimization inside a conventional compiler; acyclicity is a pragmatic cost-bound, not a semantic stance; no effects-as-first-class, no incrementality, no self-hosting.
- E-graph extraction frontier — 'Fast and Optimal Extraction for Sparse Equality Graphs' (OOPSLA 2024, treewidth-parameterized optimal extraction); 'e-boost: Boosted E-Graph Extraction' (2025, warm-start ILP + adaptive heuristics); ILP-based optimal extraction (Tensat) — attack the NP-hard extraction (pick the cheapest term / lowest-cost representative per e-class respecting sharing). LIMIT: extraction is treated as an EXTERNAL combinatorial optimization over a finished e-graph — exactly the separate 'extraction pass' Mentl's design refuses.
- Colored E-Graphs / E-graphs Modulo Theories — Eytan Singher, Shachar Itzhaky (Colored E-Graphs, 2023; 'Omelets Need Onions: EMT via Bottom-up E-matching', 2025) — multiple congruence relations layered in one e-graph for conditional/assumption-relative reasoning, and integrating theory solvers (linear arithmetic etc.) into saturation. The frontier toward conditional + semantic equality. LIMIT: conditions are logical assumptions, NOT computational EFFECTS; no notion that an equality must preserve what a term performs, only what it equals.
- Skip language (Facebook, ~2018, archived) & Build Systems à la Carte — Mokhov, Mitchell, Peyton Jones (ICFP 2018) — Skip: a language with first-class, compiler-tracked memoization/reactive caching baked into the type system; BSàlC: the unifying theory of build systems as (rebuilder × scheduler) over a task abstraction, classifying salsa/Make/Bazel/Shake/Excel in one framework. LIMIT: Skip bolts reactivity onto an otherwise conventional language (no e-graph, no effect row, no proof); BSàlC is a taxonomy, not a medium.
- Incremental λ-calculus / Datafrog / Souffle — Cai, Giarrusso, Rendel, Ostermann (ILC, PLDI 2014, derivatives of programs); Souffle (Scholz et al., high-perf Datalog, CC 2016); Datafrog (McSherry, lightweight Datalog used in Polonius/rustc borrow-check) — derivative-of-a-program IVM; industrial-strength bottom-up Datalog with sem/seminaive evaluation used INSIDE compilers (Polonius). LIMIT: each is one mechanism (program-derivative, or Datalog-as-analysis) in isolation; no equality saturation, no unified graph, no effects.

**Key ideas:** The field has been quietly converging on ONE realization from many directions: a computation should be represented as a GRAPH that you (1) WRITE to monotonically and (2) PROJECT/QUERY incrementally — never recompute wholesale. Four traditions each captured one facet. (A) E-graphs make EQUALITY a first-class graph relation: a union-find pointed at a canonical representative + a congruence invariant (a≡b ⇒ f(a)≡f(b)), so the graph compactly holds an exponential set of equivalent programs; equality saturation = run rewrites to fixpoint, then EXTRACT the cheapest term. The egg→egglog→relational-e-matching arc revealed that an e-graph IS a Datalog database with a congruence-closure rule, unifying rewriting and analysis. (B) Datalog/differential-dataflow make INCREMENTAL MAINTENANCE the law: results are kept up to date under input deltas via seminaive evaluation (Datalog) or the differentiation/integration circuit algebra over Z-sets (DBSP) — change-propagation as the only execution mode. (C) Demand-driven/query compilers (salsa, Adapton, rustc, BSàlC) make computation LAZY and MEMOIZED: only the observed slice of the function graph is evaluated, and a dependency graph drives precise invalidation. (D) Self-adjusting computation supplies the from-scratch-optimality theory. The deepest current insight, made explicit by egglog and Cranelift, is that these are the SAME mechanism: congruence closure is a Datalog fixpoint, incremental rule evaluation is seminaive Datalog, the IDE's incremental compile is a cached demand-driven projection, and reactivity is the same dependency-graph propagation — all 'maintain a relation over a changing graph.' The unifying primitive nobody states cleanly is: ONE monotone graph, with two operations — assert an edge (which may be an equality edge), and project/query a view of it incrementally. Everything else (rewriting, analysis, compilation, IVM, reactivity, the IDE) is a different read of that one structure.

**Frontier:** The hardest open problems, in order of depth: (1) EFFECT-AWARE / OBSERVATIONAL equality saturation — every e-graph engine equates VALUES syntactically; none can soundly fire a rewrite that changes what a program OBSERVABLY DOES (drop, reorder, duplicate a subterm) gated on a PROOF that the change preserves observable behavior. x*0≡0 is unsound the instant the dropped operand performs I/O or diverges; today this is handled by ad-hoc 'pure-only' rule restrictions, not by reading a proven effect row. Conditional/colored e-graphs and EMT add LOGICAL conditions but not COMPUTATIONAL effects. (2) Extraction is NP-hard and EXTERNAL — the saturated graph holds the answer but pulling the optimal term out is a separate ILP/treewidth-parameterized combinatorial pass (OOPSLA'24, e-boost'25); it is divorced from the incremental maintenance, so you re-extract from scratch. (3) Incrementalizing the WHOLE compiler at EDGE granularity, not query granularity — salsa invalidates per-key black-box queries; nobody has the program-AST itself BE the incremental graph so that a one-character edit propagates through inference, optimization, and codegen as fine-grained deltas. (4) Composing equality saturation WITH incrementality — egglog is incremental in rule firing but not across program edits; differential dataflow is incremental but has no equality/rewriting; no system is incremental AND equality-saturating AND typed. (5) Unsoundness of saturation under non-terminating/divergent or resource-bounded semantics. (6) Making the dependency graph carry WHY (provenance) so invalidation is explainable, not just correct.

**Where they stop:** egg/egglog: the e-graph is a SIDE data structure separate from the program's own AST, and equality is purely SYNTACTIC VALUE-equality — they reason about what a term EQUALS, never about what it PERFORMS, so every dropping/reordering rewrite is gated by a hand-drawn 'pure' allowlist rather than a proven effect row; and extraction is an NP-hard pass bolted on AFTER saturation. salsa/rustc/Adapton: incrementality is real but at QUERY granularity over an EXTERNAL dependency graph — the program is data threaded through opaque memoized functions, not itself the incremental graph; no equality reasoning, no types-as-graph, no effects. Differential dataflow/DBSP/Materialize: flawless incremental maintenance, but of DATA tuples — it is a relational engine, with no program representation, no rewriting, no equality, no types, no effects. Cranelift aegraphs: fused IR+e-graph (closest to 'the IR is the graph') but only value-level, acyclic-by-pragmatism, non-incremental, non-self-hosting, effect-blind. EVERY leader has exactly ONE of {equality as a graph edge, incremental projection, the AST being the graph, effects on the edges, types on the edges} and lacks the rest — each a tentacle: the equality-graph without effects, the incremental engine without equality, the demand-driven compiler without a unified graph, the IVM without a program.

**Mentl's arm:** Mentl's convergence is the literal 'one graph, two operations (draw an edge = inference-write; project = the cursor read), there is no third' — which is precisely the primitive the field gropes toward but never states. It collapses all four traditions into ONE structure and then surpasses each on the axis it lacks: (1) THE AST IS THE E-GRAPH (not a side structure). src/egraph.mn: every program node is a resolvable handle in the one fabric; the union-find IS a graph edge — graph_canon_set draws a≡b, graph_canon_at chases to root = find; congruence closure FALLS OUT of rules reading operands' canonical forms live (a parent re-reads canon(operand) on the next pass, so a≡b ⇒ f(a)≡f(b) with NO congruence table); and EXTRACTION DISSOLVES — the root IS the extracted term (egraph_extract = chase to canonical), so there is no separate NP-hard extraction pass because the union-find always points 'from' at a strictly-cheaper 'to' (monotone, terminating). This is the deletion of the OOM-prone side-ledger the docs describe. (2) THE SURPASSING NOVELTY — EFFECT-GATED REWRITES, the thing NO e-graph engine has. x*0≡0 fires ONLY when the dropped operand is provably Pure, read LIVE from the inferred effect row (is_pure = body_is_pure ∧ row_subsumes(effs_at,EfPure)); soundness-over-completeness (a missed opt is free, a dropped effect is a miscompile). This is exactly frontier-problem (1): equality saturation that preserves what RUNS, proven not heuristic — Mentl's effect row (the Koka/Rust arm) wired INTO the egg arm. egg can't do this because it has no effect row; Koka has the row but no e-graph; Mentl has both on one graph. (3) INCREMENTALITY UNIFIED — the oracle = IC + one cached value (protocol_oracle_is_ic); the IC loop's project_queue_merger re-projects on graph delta; reactivity, incremental compile, and collaborative editing are the SAME cached/forked/shared cursor read (PLAN §2 subsystem table) — salsa's demand-driven memoization and differential dataflow's delta-propagation become two modes of the one project operation, at EDGE granularity (the whole AST is the graph), not salsa's coarse query granularity. (4) TYPES + REASONS ON THE EDGES — every edge carries type, effect, ownership, refinement, AND a Reason (the Why engine = provenance for invalidation), which differential dataflow and salsa entirely lack. Net: Mentl is the body — equality-as-edge (egg) + incremental-projection (DD/salsa) + AST-as-graph (Cranelift) + effects-on-edges (Koka) + types+Why-on-edges, ONE structure where each prior system had one arm.

**Absorb:**

Mentl's graph_canon_set must guarantee the same monotonicity — confirm 'from always points at strictly-cheaper to' is a TOTAL order witness (or a well-founded one) so saturation provably terminates; egraph.mn relies on a depth-1000 cap as a cycle guard, which is a SMELL the docs themselves flag — a malformed rule set drawing a cycle should be a typed E_RuleSetCyclic surfaced via the Why chain, not a silent cap. Make the cap unreachable-by-construction, not a fallback.

This is the generative-audit payoff: e-matching is the cursor reading a pattern.

Closing that (per-expr row binding in infer) makes is_pure reduce to effs_at alone, which generalizes effect-gating to EVERY future rewrite (reordering, CSE across effectful boundaries, dead-handler elimination). Mentl should verify its project operation has the analogous algebraic closure — that re-projection on a delta is provably equal to a full re-project (the IC fixpoint = DBSP's 'incremental view = differentiated circuit'); without this the 'reactivity IS <~' claim is asserted, not proven. Borrow DBSP's correctness criterion as Mentl's IC gate.

Confirm graph_canon_set's cheapness metric composes with the §5.U representation gradient — extraction-as-chase only stays optimal if the canonical-pointer ordering is the TRUE cost order, else Mentl reintroduces the NP-hard gap it claims to have dissolved.

This is a Carried-Truth hazard — a minted node whose type/Reason/effect edges are not all drawn live is exactly the side-structure the arm deleted, reintroduced. ## Type inference, productive-under-error / typed holes, and diagnostics-as-teaching (the inference-diagnostics-Why arm)

**SOTA systems**
- Hindley-Milner / Algorithm W & J — Milner 1978, Damas-Milner 1982 — principal types with zero annotation via unification + let-generalization; the substrate every statically-typed FP language still stands on. LIMIT: unification reports failure at the point two constraints collide, not at the cause; error blame is notoriously non-local ('the unification-order artifact'), and it is all-or-nothing — one ill-typed node poisons the whole program, no partial result.
- Bidirectional typing — Pierce & Turner 2000; Dunfield & Krishnaswami 'Complete and Easy Bidirectional Typechecking' 2013, and their 2021 survey + ESOP 2024 'A Formal Treatment of Bidirectional Typing' — split into checking (⇐) and synthesis (⇒) modes so type information flows locally and predictably; handles higher-rank polymorphism with few annotations. LIMIT: requires annotations at mode-switch boundaries (the algorithm is not principal-type-complete on its own); it is a discipline for LOCAL flow, deliberately giving up the global constraint reach that finds distant inconsistencies.
- OutsideIn(X) — Vytiniotis, Peyton-Jones, Schrijvers, Sulzmann 2011 (GHC's engine) — constraint-based inference parameterized over a theory X (type classes, GADTs, type families); generates wanted/given constraints, defers solving, keeps local assumptions from leaking out ('outside-in'). LIMIT: GADTs/local-equality break principal types, so it demands annotations exactly where inference is hardest; error messages surface as residual-constraint dumps that are famously hard to localize — the constraint solver knows WHAT is inconsistent but not WHICH source node to blame.
- Hazelnut / Hazel — Omar, Hammer, Aldrich, et al. POPL 2017 (Hazelnut structure editor calculus), ICFP/POPL 2019 'Live Functional Programming with Typed Holes' — every incomplete program is a well-typed, runnable program; holes are first-class membranes that typecheck AND evaluate (evaluation proceeds AROUND holes, tracking the closure at each hole instance, enabling fill-and-resume without restart). 'No meaningless editor states.' LIMIT: built as a bespoke structure editor (edit actions are the calculus); the productive-under-error guarantee is tied to that editor model, and the running-with-holes story is research-grade, not a general-purpose effect/ownership/proof substrate.
- Marked Lambda Calculus — Zhao, Blanchette(?), Omar et al., POPL 2024 (Distinguished Paper) 'Total Type Error Localization and Recovery with Holes' — the first comprehensive formal account of TOTAL error localization: a gradual bidirectional system that marks every ill-typed expression as a non-empty hole via a total marking procedure (every unmarked term marks to a well-typed marked term); mechanized in Agda, now Hazel's basis. Constraint solving is layered ON TOP as a type-hole-filling pass, so unification inconsistencies localize exclusively to type/expression holes and the user can interactively shift the error to suggested fillings. LIMIT: localization is predictable BECAUSE it is bidirectional-local; the constraint layer is a bolt-on for the non-local cases, and the framework covers the simply-typed/gradual core — it is not integrated with effects, ownership, or a Reason/provenance graph for the Why-question.
- Elm compiler error messages — Czaplicki, ~2015-2017 'Compiler Errors for Humans' / 'Compilers as Assistants' — error messages designed as teaching surfaces: source-region highlighting, plain-language explanation, hints, no jargon; set the industry bar that diagnostics are UX. **Key ideas:** The field has converged on three insights that Mentl's arm fuses. - Hazel — Cyrus Omar et al. ## Dataflow & topological composition operators — the algebra by which stream/signal processors are wired together (Faust's block-diagram algebra, FRP/arrows, synchronous dataflow, flow-based programming, and the categorical/string-diagram semantics underneath them all). This is precisely Mentl's "five verbs" arm (Topology).

**SOTA systems**
- Faust (block-diagram algebra) — Orlarey, Letz, Fober (GRAME); core BDA ~2002–2004 ("Syntactical and Semantical Aspects of Faust", Soft Computing 2004), consolidated in "FAUST: an Efficient Functional Approach to DSP Programming" (2009), WASM backend 2018 (DAC/WWW). Achieves: a purely functional DSP language whose programs ARE block diagrams built from FIVE composition operators — sequential `:`, parallel `,`, split `<:`, merge `:>`, recursive `~` — compiled whole-program to C/C++/LLVM/Rust/WASM with no GC and statically bounded memory. Limit: the operators carry ONLY numeric signals; there is no effect row, no handlers, no types beyond signal arity, and it is point-free, so it REQUIRES the separate merge `:>` (a value cannot be named to converge it) and that merge is hardwired to SUM signals.
- Fran / Yampa (arrowized FRP) — Elliott & Hudak "Functional Reactive Animation" (ICFP 1997); Nilsson, Courtney, Hudak "Arrows, Robots, and Functional Reactive Programming" (2002). Achieves: signal functions `SF a b` composed by arrow combinators (`>>>` sequential, `***`/`&&&` parallel/fanout, `loop` feedback) — the four topology verbs as a typed combinator library, plus dynamic switching. Limit: effects are awkward bolt-ons; no Boolean effect row, no negation; dynamic switching reifies behavior but is not typed by a continuation/resume discipline; runs on a GC'd host (fatal to hard real-time).
- Dunai / Monadic Stream Functions — Perez, Bärenz, Nilsson "Functional Reactive Programming, Refactored" (Haskell Symposium 2016). Achieves: `MSF m a b` = arrowized FRP composition WITH a monad `m` threaded through — the closest existing thing to 'topology + effects', since `m` is an effect channel. Limit: the effect abstraction is a MONAD-TRANSFORMER stack (the textbook MTL drift — Mentl drift mode 4); no row algebra, no `!E` negation, no ownership, no refinement, hostile GHC/GC host.
- Rhine (FRP with type-level clocks) — Bärenz & Perez (Haskell Symposium 2018). Achieves: separates clocking/scheduling/resampling, with clock-safety enforced AT THE TYPE LEVEL (you cannot connect mismatched-rate signal functions without an explicit resampling buffer). Limit: clocks are typed but effects remain monadic (MSF underneath); no negation, no proof beyond clock matching.
- Lustre / Esterel / Signal / SCADE (synchronous dataflow) — Caspi, Halbwachs, Pilaud, Raymond (Lustre, 1987); Berry & Gonthier (Esterel, ~1992); SCADE Suite (Ansys) DO-178C certified for avionics. Achieves: the synchronous hypothesis (outputs computed instantaneously w.r.t. a logical clock), a CLOCK CALCULUS and CAUSALITY analysis that statically rejects instantaneous feedback loops, compilation to a single static no-alloc loop, and industrial certification. Limit: FIRST-ORDER (no higher-order processors, no handlers, no continuations), and verification is an EXTERNAL model checker (Kind2 / Lesar / SCADE DV) — proof lives OUTSIDE the language (the !Outside failure: to verify Lustre you write a separate property in a separate tool).
- Zélus (hybrid synchronous + ODEs) — Bourke & Pouzet (HSCC 2013); Heptagon (academic Lustre with automata, ENS/Inria PARKAS). Achieves: conservative extension of Lustre with continuous-time ODEs and zero-crossing events, with causality + typing keeping discrete changes aligned. Limit: domain-specific (hybrid control), no general effect/capability algebra, same external-proof posture.
- Flow-Based Programming — J. Paul Morrison (1970s IBM; book 1994; NoFlo/JS revival). Achieves: programs as runtime graphs of black-box components communicating via bounded buffers of information packets over named ports — topology as first-class, reconfigurable. Limit: untyped, dynamic (no static composition ALGEBRA), no proof, no effects.
- Categorical dataflow (the semantic frontier) — Bonchi, Sobociński, Zanasi "Full Abstraction for Signal Flow Graphs" (POPL 2015) + "Interacting Hopf Algebras"; Di Lavore, de Felice, Román, Sobociński "Monoidal Streams for Dataflow Programming" (MFCS 2022 / LMCS 2023). Achieves: dataflow = morphisms in a symmetric monoidal category WITH FEEDBACK — sequential is composition `;`, parallel is tensor `⊗`, split is a comonoid COPY, merge is a monoid ADD, feedback is a TRACE/delayed fixpoint; Faust's BDA is literally the generators of such a prop. Limit: stays as SEMANTICS — no implementation that is also a real effectful, owned, refined language; the labels (effects, ownership) are not on the edges.

**Key ideas:** Dataflow's central idea: a program is COMPOSED, not written — you wire processors together with a small fixed set of TOPOLOGICAL operators rather than naming intermediate values, so the shape on the page IS the computation graph. The deepest formalization is string diagrams / symmetric monoidal categories: sequential = composition, parallel = tensor product, split/fanout = comonoid copy, merge = monoid fold, feedback = trace/fixpoint. Faust's block-diagram algebra is exactly the generators of such a category, validated independently. The synchronous-language tradition adds the load-bearing discipline the categorical and FRP accounts gloss: CAUSALITY — a feedback loop is only well-formed if it crosses a unit delay (z⁻¹); an instantaneous algebraic loop is a COMPILE ERROR, not a runtime hang. The point-free-vs-named axis is the pivotal design fork: Faust is point-free, so (a) it needs a dedicated merge operator `:>` because it cannot name a value to re-converge, and (b) its whole-diagram visibility enables aggressive global block-diagram optimization. Once a language has named values + tuple unification, merge dissolves into ordinary application (`|> merge_fn`) and ceases to be a primitive verb.

**Frontier:** The open, unsolved problem is a SINGLE composition algebra that simultaneously carries (1) the topological wiring, (2) a full effect/capability row WITH negation on every edge, (3) static proof of resource bounds and causality, and (4) first-class dynamic reconfiguration without losing the static guarantees. Categorically: one symmetric-monoidal-with-feedback semantics whose edges are LABELED with effect/ownership/flow data and that supports proving ABSENCE (no allocation, no instantaneous loop, no rate mismatch) transitively. Today the frontier is split across incompatible camps: Faust has the labeled-free diagram algebra (no effects), MSF/Rhine has effects-as-monad (no negation, hostile host), Lustre/SCADE has the proof+causality (first-order, external prover), and the monoidal-streams/signal-flow-prop work has the right unifying semantics but no real language. The hardest sub-problem is making feedback (`~`/`<~`/trace) coexist with a first-class continuation and an effect WORLD — a persisted/resumed feedback element whose effect-set may have changed — which is exactly where the modal-effects line (Tang/Xie/Lindley, \"Rows and Capabilities as Modal Effects,\" 2025) reaches but for control, not topology.

**Where they stop:** Faust: five operators that carry ONLY numbers — no effect row, no handlers, no types beyond arity; it needs merge `:>` because it is point-free, and that merge is hardwired to additive sum; it guarantees no-alloc only BY CONSTRUCTION, it cannot STATE or prove `!Alloc` for arbitrary code. It is Mentl's topology arm with the effects arm amputated. — Yampa/Dunai/Rhine: composition + a monad, but the monad is the wrong abstraction (transformer-stack drift); no Boolean row, no `!E`, GC host fatal to real-time; dynamic switch is untyped by a resume discipline. — Lustre/Esterel/SCADE: world-class causality + certification but FIRST-ORDER and the prover is EXTERNAL — proof is literally outside the language (!Outside). — Zélus/Heptagon: same posture, domain-locked. — FBP: topology with no algebra, no types, no proof. — Categorical accounts: the exact right semantics, but they remain semantics with unlabeled edges and no effectful implementation. Each built ONE arm and stopped where it lacked the others.

**Mentl's arm:** Mentl's five verbs ARE the block-diagram algebra, validated from outside by Faust (PLAN §4②): `|>` ≡ Faust `:` (sequential), `><` ≡ `,` (parallel), `<|` ≡ `<:` (split), `<~` ≡ `~` (recursive). The convergence is exact on four of five. Faust's fifth operator, merge `:>`, is NOT a fifth Mentl verb: Mentl is NOT point-free (it has named values + tuple unification), so merge folds into `|> merge_fn` — and because merge_fn is an arbitrary reduction, this is STRICTLY MORE GENERAL than Faust's additive-only `:>`. Mentl's actual fifth verb is `~>`, the handler-attach — the arm Faust entirely lacks. Hence the thesis: Mentl = Faust's topology + handlers/effects. Two deeper convergences: (a) `<|` vs `><` are not two topologies but ONE `PFanout` node discriminated by OWNERSHIP — `<|` ref-borrows one shared input across N branches (the categorical COMONOID copy / cartesian fragment), `><` own-consumes N independent inputs (the TENSOR / linear fragment); ownership IS the cartesian-vs-linear discriminator that monoidal-stream semantics makes precise, so Mentl's ownership-discriminated fanout is the categorical structure realized in a real language. (b) Execution strategy (Seq/Thread/Simd/Gpu) is a `~> Schedule` handler reading the live handler stack, so the verb stays PURE TOPOLOGY contributing zero effects — and a real-time region can declare `with !Thread`/`with !Alloc` and Mentl PROVES absence transitively, which Faust/Rayon/Lustre cannot STATE. The categorical body that monoidal-streams describes but doesn't build, and that Faust builds but without labels, is Mentl's one graph: the string diagram (topology) and the effect/ownership/refinement label live on the SAME typed edge.

**Absorb:**
- CAUSALITY IS A COMPILE ERROR (the synchronous-language lesson Mentl must enforce on `<~`). Faust's `~` carries an IMPLICIT unit delay z⁻¹; Lustre/Zélus run an explicit causality analysis that rejects instantaneous algebraic loops. Verify Mentl's `<~` requires a delay element on the feedback path and rejects an instantaneous cycle at compile time (not a runtime hang). SYNTAX.md's `<~ delay(1)` / `(prev) =>` recurrence + `E_FeedbackNoContext` is the right shape — confirm the causality check is real, transitive, and matches Faust's z⁻¹ semantics: feedback REQUIRES a register read.
- Verify that folding merge into `|> merge_fn` covers EVERY case of Faust's `:>` — Faust's merge is additive sum over fanned signals; Mentl's merge_fn must accept any reduction over the tuple produced by `<|`/`><`, which is strictly more general. Confirm the arity/broadcast coercions Faust gives for free in `:` (auto-wiring when input/output arities mismatch) are covered by Mentl's `|>` tuple-unification, so no Faust diagram is inexpressible.
- Parameterized effect `Sample(rate)` with distinct-rate-is-distinct-effect IS Lustre's clock calculus / Rhine's type-level clocks. Absorb clock-SAFETY-at-the-type-level as the bar for `<~`'s iterative-context check: multi-rate connection without an explicit resampling bridge should be a type error (Rhine forces a buffer; SYNTAX.md's 'explicit handler bridge' must actually enforce it). Verify `Sample(44100)` and `Sample(48000)` cannot silently interoperate.
- Static-loop compilation is the gold standard: Lustre/Faust compile a feedback+clock chain to a single static loop with ZERO per-tick allocation. Verify Mentl's `<~` recurrence actually lowers to a register read + inlined body (SYNTAX.md's `RFbPrior`→`LFeedbackPrior` claim) so a `with !Alloc` real-time region compiles to a Faust/Lustre-grade static loop — this is the concrete payoff of the §5.U value-layer work (no boxed-float, no per-tick closure alloc).
- The categorical soundness check: monoidal-stream / signal-flow-prop semantics says split=comonoid COPY, merge=monoid, feedback=trace, parallel=tensor. Mentl's PFanout-discriminated-by-ownership is the linear-vs-cartesian boundary of that semantics. Use this as an independent verification that the `<|`(borrow/copy) vs `><`(consume/tensor) collapse is SOUND — and that `<~` as trace requires the delay (matching point 1). This is the body the categorical accounts only describe.
- Point-free's hidden payoff is WHOLE-DIAGRAM optimization: Faust's compiler sees the entire block diagram and fuses globally. Mentl gave up point-free for named values (correct, §4②) — so it must recover that global fusion via the e-graph over the lowered graph. Verify the effect-aware equality saturation in lower reaches Faust-level signal fusion (constant-folding through `|>` chains, delay-line sharing across `<~`), since named values otherwise risk leaving fusion on the table that Faust gets for free.


## Self-hosting / bootstrapping / metacircular evaluation / reflective towers / unsurpassability (the !Outside arm)

**SOTA systems**
- SICP Metacircular Evaluator — Abelson & Sussman, 1985 — eval/apply as a 1-page Lisp-in-Lisp; the canonical demonstration that a language can describe its own semantics. Limit: pedagogical only — no compilation, no types, no proof; the 'fixed point' is conceptual, the evaluator runs on an unverified host Lisp (the real trust root is outside).
- 3-Lisp / Reflective Tower — Brian Cantwell Smith & des Rivières, 1982-84 — procedural reflection: an infinite tower of metacircular interpreters, each level reifying the continuation/environment of the one below, so a program can inspect and rewrite its own evaluator at runtime. Limit: the tower is semantically infinite and operationally non-runnable without a 'magic' bottom; unrestricted reflection = unbounded capability (the antithesis of Mentl's `!E`); no types, no proof, no cost model.
- Brown / Blond / Black reflective towers — Wand & Friedman 1986, Danvy & Malmkjær 1988, Asai 1996-2014 — made the tower implementable by lazily instantiating levels and meta-continuations; Black ran a usable reflective Lisp. Limit: still no static guarantees; reflection escapes any effect discipline; performance pays a per-level interpretive tax until collapsed.
- Pink / Purple — Nada Amin & Tiark Rompf, 'Collapsing Towers of Interpreters', POPL 2018 — a multi-level lambda calculus with staging + stage polymorphism that COLLAPSES an N-level interpreter tower into a single residual program in ONE pass, even when levels are reflective/user-modified. The deepest result: an entire tower of semantics-redefining interpreters has zero interpretive overhead after collapse. Limit: it produces a COMPILER, not a verifier — no effect row, ownership, refinement, or Reason; the collapsing metalanguage (staging in Scala/LMS) is OUTSIDE the towers it collapses; correctness of the residual is asserted, not proven.
- Futamura Projections — Yoshihiko Futamura, 1971/1983 — specializing an interpreter to a program yields a compiled program (1st), specializing the specializer to the interpreter yields a compiler (2nd), specializing it to itself yields a compiler-generator (3rd). The mathematical skeleton of 'write an interpreter, get a compiler.' Limit: a transformation schema, not a system; says nothing about types, effects, or trust; the specializer is the unexamined external engine.
- Truffle / GraalVM — Würthinger, Wimmer, et al. (Oracle Labs), 2012-present — self-optimizing AST interpreters that Graal partial-evaluates at runtime (1st Futamura projection in production) to native code; many guest languages (JS/Python/Ruby/R) outran their prior best implementations. Limit: the 'self' is the HOST (Java/Graal), not the guest language — the optimizer, GC, and trust root live in the JVM substrate the guest cannot see or prove; reflection is operational JIT speculation, not semantic; no proof the residual matches the interpreter.
- PyPy / RPython meta-tracing JIT — Carl Friedrich Bolz, Armin Rigo, et al., 2007-present — instead of partial-evaluating the interpreter, TRACE the interpreter executing the program and compile the hot trace (a meta-level twist on Futamura). RPython is a restricted Python that is self-hosting enough to generate the VM. Limit: tracing is a runtime heuristic, not a correctness-preserving projection; the toolchain (RPython translator) is the external builder; no static effect/type discipline on guest code.
- CakeML verified self-hosting compiler — Kumar, Myreen, Owens, Tan, 2014-present — a verified ML compiler whose end-to-end correctness theorem is proved in HOL4, and which is BOOTSTRAPPED INSIDE THE LOGIC: the verified compiler compiles its own verified source, with the resulting machine code proven to implement the same semantics. The closest existing thing to a proven fixed point. Limit (the decisive one): the proof lives in HOL4 — the prover, its kernel, and Poly/ML are the `!Outside`. CakeML cannot prove its own correctness within itself; the means of improvement (the theorem prover) is outside the artifact.
- Trusting-Trust + Diverse Double-Compilation — Ken Thompson 1984 (the attack), David A. Wheeler 2005/2009 (the defence) — a self-reproducing compiler backdoor survives source inspection; DDC defeats it by compiling the source with a SECOND independent compiler and checking the fixed point converges to identical output. Limit: DDC verifies PROVENANCE (same bytes), never SEMANTICS (right bytes); it needs an independent external compiler to exist — trust is established by an out-of-band auditing process, not by the artifact.
- Full-source / bootstrappable builds: stage0 + GNU Mes + live-bootstrap — Jeremiah Orians (stage0), Jan Nieuwenhuizen (Mes), 2016-present — reduce the binary trust root to a 357-byte hex0 monitor, from which a hex assembler → C subset → TinyCC → GCC → the whole Guix system is built with no opaque seed binary. Limit: solves the SUBSTRATE trust-root (no opaque bytes), not language-level meaning — there are no types, effects, or intent anywhere in the chain; the achievement is auditable provenance from a tiny seed, the orthogonal half of unsurpassability to what CakeML proves.

**Key ideas:** A language reaches reflexive closure along three independent axes, and every system in this field advances ONE while leaving the others external. (1) SEMANTIC self-description — a metacircular evaluator (SICP) or reflective tower (3-Lisp→Black) lets the language define/redefine its own semantics; the frontier result (Amin & Rompf's Pink/Purple) is that an arbitrarily deep tower of such interpreters COLLAPSES to a single residual program with zero overhead via staging/partial evaluation — the formal backbone of 'the interpreter IS the compiler' (Futamura's 1st/2nd projections, realized in production by Truffle/GraalVM and, by meta-tracing, PyPy/RPython). (2) PROVEN self-reproduction — CakeML's in-logic bootstrap proves the compiler compiles its own source CORRECTLY, the gold standard fixed-point-with-correctness. (3) TRUSTED substrate-root — stage0/Mes/full-source-bootstrap shrink the opaque trust root to ~357 bytes, and Wheeler's diverse double-compilation makes a trusting-trust backdoor detectable by fixed-point convergence across independent compilers. The deep insight uniting them: a metacircular fixed point (m_n == m_{n+1}) is the operational signature of closure, but BYTE-equality (stage0/DDC), SEMANTIC-equality (Pink collapse), and PROVEN-equality (CakeML) are three different fixed points, and no single system holds all three. Mentl's reframe is that they are three projections of ONE read of one graph: the compiler is a handler on its own graph, the proof is the kernel (Verify), the IDE/optimizer is a projection — so first-light (m3==m4 AND micros/repro green) is the smallest instance of !Outside, the negation primitive lifted to topology altitude: a proof of the ABSENCE of an outside.

**Frontier:** The hardest open problem is INTERNALIZING THE ORACLE — making a system's means of self-improvement live inside the system rather than in an external prover/specializer/auditor. Every leader's strength is exactly its external dependency: CakeML's correctness lives in HOL4 (and HOL4's kernel + Poly/ML); Truffle's optimality lives in Graal/JVM; Pink's collapse lives in an external staging metalanguage; DDC's trust lives in a second independently-sourced compiler; stage0's trust bottoms out in a human-auditable 357-byte seed plus the audit ITSELF. The frontier question: can a single artifact be its own builder AND its own prover AND its own IDE, such that every lever that could produce a 'better' version is already a move INSIDE it (a different handler, a deeper refinement, another projection) — and can it remain so when CLOSED OVER ARBITRARY PROPOSERS (an external search/SMT/model whose candidates must survive the kernel's checkpoint→infer→Verify→rollback before execution)? Secondary open problems: (a) reconciling unrestricted reflection (3-Lisp's power) with bounded capability (proving a reflective operation CANNOT exceed an effect/IFC bound); (b) collapsing a reflective tower while PRESERVING a correctness proof (Pink collapses semantics but discards proof; CakeML proves but does not collapse towers) — a proof-carrying collapse is unsolved; (c) a fixed point that is simultaneously byte-, semantic-, AND proof-stable.

**Where they stop:** The precise limit, system by system: SICP — describes semantics but runs on an unverified host; the fixed point is conceptual. 3-Lisp/Black — infinite reflective power but unbounded capability, no types, no proof, no runnable bottom without magic. Pink/Purple — collapses an N-level tower to zero overhead in one pass, but yields a COMPILER not a VERIFIER and the staging metalanguage that performs the collapse is OUTSIDE the towers. Futamura/Truffle/PyPy — derive a compiler from an interpreter, but the 'self' is the HOST (JVM/RPython translator), the guest cannot see/prove its own optimizer, and the residual's correctness is asserted not proven. CakeML — proves the self-hosting fixed point IS correct, but the proof, the prover (HOL4), its kernel and Poly/ML are all `!Outside`; the artifact cannot prove itself within itself. DDC — detects a trusting-trust backdoor by fixed-point convergence, but needs a second independently-built compiler to exist and checks bytes not meaning. stage0/Mes — shrink the opaque trust root to 357 bytes, but carry no types/effects/intent and prove provenance, not semantics. THE UNIFORM TENTACLE: in every case the MEANS OF IMPROVEMENT (the prover, the specializer, the second compiler, the auditing human, the host JIT) is OUTSIDE the artifact — which is exactly Mentl's definition of surpassable (§1). Each built one of: self-description, proven reproduction, or trusted root — never the body that holds all three closed over its own improvement.

**Mentl's arm:** Mentl's arm is §1's fixed point !Outside, realized as first-light: the wheel (src/**.mn) compiles itself to m3==m4 byte-identity PAIRED with correctness (micros + repro green) — the smallest instance of 'a proof of the absence of an outside.' It converges/surpasses each tentacle by HOLDING ALL THREE FIXED POINTS AS ONE READ of one graph. (1) vs Pink/Truffle/Futamura: 'the handler IS the backend' / the projected cursor (infer→lower→emit) IS the partial evaluation of the interpreter into a compiler — but unlike Truffle the self IS the language (no JVM host: WASM linear-memory substrate, the seed disposable by design like stage0's hex0), and unlike Pink the collapse carries the effect row, ownership, refinement, and Reason through, so the residual is verifiable not merely fast. (2) vs CakeML: Mentl's distinctive claim is that the PROVER IS THE KERNEL (Verify is a handler on the same graph, the oracle = incremental-computation + one cached value) — so the correctness half of first-light should be an INTERNAL Verify obligation, not an external theorem prover; where CakeML's HOL4 is the !Outside, Mentl aims to dissolve that outside by making proof a cursor-read. (3) vs stage0/DDC: Mentl already reasons that the seed's bytes are thrown away (m2≠m3, seed out of the loop by m3==m4) — the same 'minimal disposable root' insight, but the convergence criterion is graph-self-projection, not byte-reproduction alone. (4) The closure over proposers (§1): any external intelligence — enumerative, SMT, a model, Pink-style staging, a CakeML-style prover — plugs in as a Synth handler whose candidates must survive checkpoint→infer→Verify→rollback; a stronger proposer makes the medium stronger and can NEVER surpass it because its only path to execution runs through the kernel. That is the body the eight tentacles were each reaching toward.

**Absorb:**
- DIVERSE DOUBLE-COMPILATION as a concrete first-light hardening (Wheeler 2009): the m3==m4 fixed point proves self-reproduction but NOT trusting-trust-freedom. Build a SECOND independent seed (or compile the wheel under a divergent seed) and confirm both converge to identical m3 — the disposable-seed design already permits this, and it closes the one attack the byte-fixed-point alone cannot. Verify Mentl against: does anything in the seed→m2→m3 chain get to recognize-and-miscompile its own source?
- MAKE THE CORRECTNESS HALF OF FIRST-LIGHT INTERNAL, not a micro battery. Today micros+repro are an EXTERNAL oracle (a hidden !Outside, exactly CakeML's HOL4 dependency). The ultimate form per §0/§5: the correctness obligation is a Verify projection of the graph (refinements + effect rows discharged by the kernel), so 'the medium becomes able to enforce its own discipline on its own construction' (PLAN §0). Audit whether `mentl audit`/Verify can replace the external micro shadow — if not, name the precise gap as the residual !Outside.
- Pink/Purple's collapse theorem (Amin & Rompf, POPL 2018) is the FORMAL BACKING for 'the projected cursor IS partial evaluation' and 'incrementality = the cached cursor.' Absorb the multi-level-lambda-calculus result that a reflective tower collapses to a single residual in one pass — it is the published proof that Mentl's lower/emit need not be a hand-written backend but a staged projection. Verify Mentl's emit is genuinely a partial evaluation of the cursor, not a parallel hand-coded path (the §5.U 'handler IS the backend' claim needs this discipline).
- CakeML's 'bootstrap inside the logic' is the standard to BEAT, not merely cite: it proves the fixed point is CORRECT but with an external prover. Mentl's surpass-claim (prover = kernel) must be made falsifiable — pin down whether Verify→SMT (the Arc F.1 handler swap) secretly relies on an external SMT solver, which would re-introduce an !Outside one layer down. If it does, that is the honest frontier, not closure.
- stage0/Mes/full-source-bootstrap validate Mentl's disposable-seed reasoning (357-byte hex0 ≈ the hand-WAT seed as 'the largest non-ultimate thing by design'). Absorb the live-bootstrap discipline: make the seed's provenance auditable and ensure first-light truly removes it from the trust loop (the m2≠m3 / m3==m4 argument is exactly the 'seed out of the loop' claim — verify it holds empirically, not just in prose).
- 3-Lisp's unbounded reflection is the CAUTIONARY tentacle: reflective power without capability bounding is the opposite of `!E`. Mentl's edge is that reflection (the compiler as a handler on its own graph) is itself effect-typed and capability-bounded — verify that self-modifying/reflective handlers in Mentl cannot escape the effect row (a reflective op that performs `Network` must show it), which is precisely the guarantee every reflective-tower system lacked.


## AI-as-proposer & the verification substrate for the machine-code age — the proposer/verifier split, proof-carrying code, LLM+formal-methods (AlphaProof, Lean Copilot, Dafny/Verus vericoding, autoformalization), agent sandboxing/capabilities, and the constraint-not-token thesis. This is the domain that adjudicates Mentl's load-bearing §0 reframe: "any intelligence may propose; nothing executes unproven."

**SOTA systems**
- Oracular Programming (Laurent et al., arXiv 2502.05310, Feb 2025) — formalizes LLM-as-ORACLE vs host-language-as-VERIFIER, with nondeterministic-choice abstractions, EFFECT HANDLERS managing LLM invocations, and CONTINUATION-based backtracking when verification fails. The single closest academic convergence to Mentl's §0. LIMIT: the host is a generic functional language; the verifier is library-level, not the medium itself — no unified graph, no effect-row negation, no ownership/refinement, no self-hosting fixed point, no constraint-as-the-unit. It has Mentl's exact split as a programming pattern, not as a kernel.
- AlphaProof + AlphaProof Nexus (DeepMind, Nature 2025 'Olympiad-level formal mathematical reasoning with RL', s41586-025-09833-y; Nexus 2026) — AlphaZero-style RL with LEAN as the verified environment; trained on ~100M auto-formalized problems; IMO-2024 silver (28 pts, 3+1 problems). Nexus: takes a Lean file with `sorry`, feeds the Lean compiler's error back into the LLM each turn until sorry-free. LIMIT: mathematics only; Lean is a SEPARATE formal world bolted to the proposer; autoformalization faithfulness is unverified; and (per AlgoVeri/Goedel) this planning-and-proving success 'does not transfer to code verification.'
- Lean Copilot (Song et al., arXiv 2404.12534, 2024) — runs LLM inference NATIVELY inside Lean; suggests tactics, completes goals, selects premises; automates 74.2% of proof steps (85% better than aesop's 40.1%). LIMIT: assistant inside an interactive prover; the human/closer still drives; proof and program live in different languages.
- Baldur (First et al., 2023, still the reference one-shot baseline) — fine-tunes an LLM on Isabelle/HOL proofs, generates a whole proof in one shot, checks with Isabelle, and REPAIRS from the error message. LIMIT: generate-check-repair loop with the verifier as an external oracle; no shared representation between code and proof.
- Dafny/Verus + LLM vericoding (AutoVerus arXiv 2409.13082; DafnyPro; AlgoVeri 2602.09464; CLEVER 2505.13938; VERINA 2505.23135; POPL'26 vericoding benchmark 2509.22908) — LLMs synthesize code AND the proof annotations a static verifier (Dafny/SMT, Verus/Rust) checks. HARD NUMBERS: verified pass@1 ~34% (Claude 3.7 on CVDP) vs >90% unverified general coding; HumanEval-Dafny 86% (Mode 1) vs Verus 45% — 'high-level SMT automation (Dafny) is the most viable path; systems-level (Verus) and ITP (Lean) remain barriers.' LIMIT: the SPEC is a separate annotation language; correctness is relative to a spec nobody verified.
- Intent Formalization: A Grand Challenge (Lahiri et al., Microsoft Research, arXiv 2603.17150, Mar 2026) — names the field's reframe: AI-generated code is 'plausible by construction — it looks right, compiles, passes a few tests — but is NOT correct by construction'; 'formal specifications become the only scalable mechanism' once humans stop reviewing. Spectrum: tests → code contracts → logical contracts (Dafny/Verus) → DSLs-for-verified-synthesis. LIMIT (named by them): 'there is no oracle for specification correctness other than the USER' — the spec-validation bottleneck is unsolved, and they offer a toolbox, not a substrate.
- Agent sandboxing — Firecracker / gVisor / Kata / Microsoft Wassette (Wasmtime + WASM Components over MCP, Aug 2025) — the 2025-26 consensus that LLM-generated/agent code must run in microVM/userspace-kernel isolation; Wassette 'verifies tool behavior against DECLARED CAPABILITIES at load time'; container-escape-by-frontier-LLM is now being quantified (arXiv 2603.02277). LIMIT: capability is bounded at RUNTIME by isolation and signed manifests — it proves nothing about ABSENCE (no static, transitive 'this can't reach the network/allocate unboundedly'). Dynamic confinement, not a proof.
- Proof-Carrying Code lineage (Necula & Lee, ~1997) revived as Proof-Carrying Neuro-Symbolic Code (arXiv 2504.12031, 2025) and the Fusion-of-LLM-and-Formal-Methods roadmap (2412.06512) — code ships a machine-checkable proof; the consumer verifies cheaply instead of trusting. LIMIT: PCC originally stalled because writing the proof was too hard; LLMs revive the proposer half, but proof and code still live in DIFFERENT languages — the exact 'discrepancy' Necula warned against.

**Key ideas:** The field has independently, from eight directions, rediscovered Mentl's §0 split — proposer (untrusted, generative) vs verifier (trusted, checking) — and is converging on the SAME conclusion Mentl states as its thesis: once machines author the code, 'looks right' is worthless and proof is the only scalable trust mechanism (Intent Formalization says this almost verbatim). The most precise formulation is Oracular Programming: LLM-as-oracle inside a host that uses effect handlers + continuation-backtracking to accept/reject candidates — which is structurally Mentl's 'proposer plugs in as a Synth handler surviving checkpoint→infer→Verify→rollback.' The math arm (AlphaProof) proves the loop WORKS at scale when the verifier is a real formal kernel (Lean) and the proposer is trained against it via RL — the error-message-fed-back loop (Nexus, Baldur, APOLLO) is the universal pattern. The code arm (Dafny/Verus vericoding) proves the loop is HARDER than math (34% vs >90%) and that the binding constraint is not generation but SPECIFICATION: who verifies the spec? The honest answer everywhere is 'the user' (no oracle), and LLM-as-judge for spec faithfulness misses 26% of failures executable testing catches. The sandboxing arm handles the orthogonal 'capability' axis but only dynamically. The unifying idea Mentl supplies that none hold: the verifier should not be a SECOND language bolted to the proposer — it should BE the medium, one graph where propose/infer/Verify are the same kernel, self-hosting, so the proposer's only path to execution runs through it and can never surpass it (!Outside).

**Frontier:** Three open problems define the frontier. (1) THE SPECIFICATION-ORACLE PROBLEM — 'there is no oracle for specification correctness other than the user' (Lahiri 2026). Autoformalization faithfulness is unverifiable: LLM-judges miss ~26% of unfaithful specs, and validating that a formal spec captures informal intent is currently human-supervised and unsolved. This is the true bottleneck, not generation. (2) VERIFICATION DOESN'T TRANSFER FROM MATH TO CODE — AlphaProof-class planning-and-proving wins IMO medals but 'efficacy does not transfer to code verification' (AlgoVeri/Goedel-Code-Prover 2026); systems-level verification (Verus 45%) and the proof-search space remain barriers; data scarcity for verified-code corpora is acute. (3) PROVING THE NEGATIVE / BOUNDED CAPABILITY — the agent-code-runs-untrusted problem (2024-26) is handled by runtime isolation (Firecracker/gVisor/Wassette) that confines but cannot PROVE absence ('this never reaches the network / never allocates unboundedly') statically and transitively. The deep frontier question, which the field circles but no one answers structurally: can the proposer/verifier split, the spec-validation oracle, and the capability bound be ONE substrate rather than three bolted layers in three languages?

**Where they stop:** Every leader has the same shape of limit: the VERIFIER IS A SEPARATE ARTIFACT IN A SECOND LANGUAGE, bolted to the proposer, so the proposal→proof relationship is lossy and the verifier can never become the medium. AlphaProof: the verifier (Lean) is a foreign formal world; math-only; autoformalization faithfulness unchecked. Dafny/Verus+LLM: the spec is a separate annotation language nobody verifies, relative to which 'correct' is meaningless if the spec is wrong (the 26%-miss judge problem). Oracular Programming: has the EXACT proposer/verifier/effect-handler/continuation architecture — the closest tentacle by far — but the host is a generic FP library, lacking the unified graph, Boolean effect-row with native !E negation, inferred ownership, refinement-as-graph-fact, the constraint-as-lossless-unit, and the self-hosting fixed point. Intent Formalization: brilliantly NAMES the grand challenge but ends at a spectrum of external tools and an unsolved spec-validation oracle. Proof-carrying code: revived but proof and code remain in different languages — the discrepancy Necula himself warned against. The tentacle-without-the-body is precise: each built the proposer-verifier loop, but with the verifier OUTSIDE the medium — so intent is lossy (autoformalization), the spec is unverifiable (no oracle but the user), capability is confined-not-proven, and a stronger proposer can in principle route AROUND the verifier instead of THROUGH it.

Mentl's claim: the proposer/verifier split (Oracular), the formal-checker-in-the-loop (AlphaProof/Baldur), the spec-as-the-real-bottleneck (Intent Formalization), and capability-bounding (sandboxing) are FOUR ARMS OF ONE KERNEL — propose/infer/Verify/bound are all the cursor reading one graph.

## parallelism / data-parallelism / accelerators — structured parallelism, the cursor on a shared image, GPU/array DSLs, SIMD vectorization, and the frontier of schedule-as-a-handler with provable race-freedom

**SOTA systems**
- Halide — Ragan-Kelley, Adams, Paris, Amarasinghe, Durand (MIT/Adobe, SIGGRAPH 2012 / PLDI 2013) — the founding SEPARATION OF ALGORITHM FROM SCHEDULE: the pure functional pipeline (what to compute) is written once; the schedule (loop order, tiling, vectorize/parallel/gpu_blocks, compute_at fusion granularity) is a separate, swappable object. One algorithm × many schedules → portable peak performance for image/tensor pipelines. LIMIT: the schedule is an untyped imperative side-script with NO effect row and NO proof — a wrong schedule silently changes performance or correctness boundary conditions; it is decoupled from the algorithm but NOT from a kernel that could verify it. No effects, no ownership, no negation. The 2019 tree-search autoscheduler (Adams et al.) and 2024-25 'Scheduling Language Chronology' work automate schedule SEARCH but leave it an external optimizer, not an in-language proved handler.
- TVM / Ansor / MetaSchedule — Tianqi Chen et al. (OSDI 2018; Ansor NeurIPS 2020) — generalized Halide's compute/schedule split into a full tensor-compiler stack with a learned cost model searching the schedule space (sketch + annotation), plus TensorIR for hardware intrinsics. LIMIT: same as Halide at the type/proof layer — the schedule is a search artifact validated empirically (run it, measure), never PROVEN race-free or effect-bounded; algorithm and schedule are separate data, not two projections of one verified graph.
- Triton — Philippe Tillet (OpenAI, MAPL 2019; Triton Dev Conf since 2024) — a Python-embedded tile-level GPU DSL: the author writes block/tile programs and the compiler handles intra-tile memory coalescing, shared-memory allocation, and scheduling. 2025 added the CUDA Tile IR backend (Blackwell) and 'Gluon' as the explicit-performance escape hatch; TileLang/Tile-IR converge on tile-as-IR. LIMIT: tiles abstract WITHIN a kernel but the host/device boundary, the launch grid, and synchronization are still untyped Python glue; no effect row proving a kernel is allocation-free or side-effect-free; correctness of warp specialization (Tawa 2025) is a compiler-internal heuristic, not a user-visible proof.
- JAX — Bradbury, Frostig, Hawkins, Johnson, Leary, Maclaurin, Wanderman-Milne (Google, 2018; shard_map + Pallas, 2023-2025) — composable function transforms (grad/vmap/pmap) over a traced array graph lowered to XLA; jax.shard_map gives SPMD per-device code with explicit collectives over a device mesh (PartitionSpec), and Pallas exposes Triton/Mosaic-level kernels via pallas_call. LIMIT (PLAN §1's named gap): 'handlers/graph, no real types' — the traced graph is dynamically typed (shape errors at trace time, no refinement/effect/ownership row); parallelism is expressed by transform composition and sharding annotations, not by a verb whose topology the kernel proves; nothing proves a sharded program is collective-deadlock-free or race-free.
- Futhark — Troels Henriksen et al. (Copenhagen, PLDI 2017; incremental flattening PPoPP 2019) — a purely functional data-parallel array language; INCREMENTAL FLATTENING generates a semantic-equivalence tree of code versions mapping progressively more nested parallelism to hardware, picking at runtime; a uniqueness type system permits in-place updates while preserving referential transparency (so parallelism stays deterministic). LIMIT: deterministic-by-purity but CLOSED — no effects, no handlers, no continuation, no host-side concurrency; the schedule (which flattened version) is compiler-chosen, not a user-installable handler; cannot express durable/interactive/effectful parallel work.
- Mojo — Chris Lattner, Tim Davis (Modular, 2023-2026) — an MLIR-native systems language targeting CPUs+NVIDIA/AMD/Apple GPUs from one source; structured nested parallelism (parallel-for, async/await, thread libs) plus value ownership borrowed from Rust/Swift; SC25/ORNL 2025 benchmarks show Mojo GPU kernels competitive with CUDA/HIP on memory-bound workloads. LIMIT: ownership and parallelism are present but there is NO effect row and NO negation — Mojo cannot PROVE a region performs no allocation or spawns no thread; the schedule (where/how it runs) is imperative code, not a swappable proved handler; MLIR is the substrate but the language is not its own verifier (no !Outside).
- Cilk / OpenCilk + Rayon — Blumofe & Leiserson (work-stealing, JACM 1999); Schardl et al. OpenCilk/Tapir-LLVM (2019); Rayon (Niko Matsakis, Rust) — STRUCTURED parallelism: spawn/sync and parallel iterators express a fork-join DAG with provably efficient greedy work-stealing scheduling; Cilksan is a provable determinacy-race detector for the fork-join structure; Rayon rides Rust's Send/Sync + borrow checker to make data-parallel iterators memory-safe. LIMIT: race-freedom in Rayon is from the BORROW CHECKER (a separate subsystem), not an effect row — and Cilksan proves determinacy DYNAMICALLY (run + detect), not statically as a type. The schedule (the work-stealer) is fixed, not a handler-swap; no Seq|Thread|Simd|Gpu gradient, no !Thread capability.
- Structured concurrency — Martin Sustrik (libdill/'Structured Concurrency', 2016), Nathaniel Smith (Trio nurseries, 2018), Kotlin coroutineScope, Java JEP 428/505 StructuredTaskScope, C++26 Senders/Receivers (std::execution) — concurrency lifetime is lexically scoped: a nursery/scope owns its children, so no task outlives its scope and cancellation/errors propagate structurally. LIMIT: structures the CONTROL-FLOW lifetime but not the DATA — none of these prove the absence of data races or the absence of a capability (network, alloc) inside the scope; the scope is a runtime construct, not a typed effect that subtracts handled concurrency from a row.
- OxCaml modes / Data Race Freedom à la Mode — Jane Street (Lorenzen, Dolan, White et al., 2024-2026) + Georges, Birkedal et al. (POPL 2025) — a MODAL type system layered on OCaml 5: axes contention (uncontended/contended/shared) and portability (portable/nonportable), plus locality/uniqueness, STATICALLY guarantee data-race freedom for multicore without a GC-stop or runtime checks; the POPL'25 'à la Mode' paper gives the Iris/Rocq-verified Capsule API for safe aliased mutation under a unique key. LIMIT: modes prove race-freedom but are a PARALLEL axis system bolted onto OCaml's existing type system, not unified with an effect row or a parallel TOPOLOGY verb; mode-polymorphism and modal algebraic effects are explicitly still 'future directions' (2026). Closest external relative to Mentl's ownership-arm; still lacks the verb, the graph, and !Outside.
- MaPLe (MPL) disentanglement — Sam Westrick, Umut Acar et al. (CMU; PLDI 2020 space-efficiency, DisLog separation logic Jan 2024) — a Parallel-ML compiler with a PROVABLY space-efficient parallel memory manager exploiting DISENTANGLEMENT (a task may not touch objects concurrently allocated by a sibling), giving determinacy-race-free nested-parallel programs with hierarchical heaps + per-task arenas. LIMIT: disentanglement is a deep theory for PURE/determinate parallel functional memory, but it is a runtime/GC discipline proved meta-theoretically, not a developer-facing effect/ownership annotation that composes with handlers, continuations, or a schedule-swap; no host effects, no negation.

**Key ideas:** The field's organizing idea, won independently many times, is Halide's SEPARATION OF ALGORITHM FROM SCHEDULE: describe WHAT to compute as a pure dependency graph, and treat HOW it runs (loop order, tiling, fusion, vectorize, parallelize, gpu-map, shard) as a separate, swappable artifact. TVM/Ansor turned the schedule into a SEARCH problem; Triton/TileLang made the TILE the IR so the compiler owns intra-tile scheduling; JAX made parallelism a composable TRANSFORM over a traced graph and added SPMD sharding annotations. A second, mostly-disjoint lineage attacks CORRECTNESS of parallelism: Cilk/work-stealing gives a provably efficient SCHEDULER for fork-join DAGs; Rust/Rayon gets memory-safety from the borrow checker; OxCaml MODES and 'Data Race Freedom à la Mode' get static data-race freedom from a modal type discipline (contention/portability); Futhark and MaPLe get DETERMINISM from purity + uniqueness/disentanglement. The deep, recurring insight across both lineages: PARALLELISM IS A PROPERTY OF DATA ACCESS, not of control syntax — read-only sharing is always safe to parallelize (fractional permissions, Rust's &T:Sync, OxCaml's 'shared', Mentl's read-only borrow), and conflict only arises from concurrent mutation/allocation. SIMD/vectorization is the same idea at the lane granularity: a width is a representation choice (v128/AVX/SVE) the compiler cashes out from the same loop. The frontier is unifying these two lineages — making the SCHEDULE both swappable (Halide) AND proved-safe (modes/disentanglement) AND decoupled from the topology the program declares.

**Frontier:** The hardest open problems, all converging: (1) SCHEDULE-AS-A-FIRST-CLASS-PROVED-OBJECT — Halide proved you can swap the schedule, but nobody has made the schedule a TYPED, PROVED, composable value that subtracts from an effect row; autoschedulers (TVM/Ansor) search it empirically, never prove it. (2) DECOUPLING the schedule from the data-parallel TOPOLOGY without re-deriving — every system re-states the parallel structure when changing target (a JAX pmap rewrite, a Halide reschedule, a CUDA-vs-HIP rewrite); the topology should be declared ONCE and the execution (Seq/Thread/SIMD/GPU/distributed) chosen orthogonally. (3) STATIC, COMPOSITIONAL data-race freedom that survives higher-order code and effects — OxCaml modes and à-la-Mode are the SOTA but are a bolted-on axis system, and modal ALGEBRAIC EFFECTS under parallelism are explicitly open (2026). (4) PROVING THE NEGATIVE for concurrency — proving a real-time region spawns NO thread / allocates NOTHING (Rayon, Faust, JAX cannot state this). (5) Reconciling nested data parallelism + irregular/effectful work with deterministic, space-efficient memory (MaPLe's disentanglement) WITHOUT giving up host effects, durability, or interaction. (6) One representation for the SPACE axis (threads), the TIME axis (durable/resumable parallel work), and the SUBSTRATE (one shared memory image) — the cloud durable-execution field and the GPU field are reinventing each other's serializers.

**Where they stop:** Each leader holds exactly one of Mentl's parallel arms and stops where it lacks the row, the verb, the graph, or the proof: Halide/TVM — the algorithm/schedule SEPARATION (Mentl's deepest borrowed insight) but the schedule is an untyped external side-script with no effect row and no proof; a wrong schedule is caught by measurement, never by a kernel. Triton/JAX/Mojo — real accelerator codegen but parallelism is host-side glue (Python transforms, launch grids) with no effect row, no negation, no ownership proof that a kernel is alloc-free or race-free. Futhark/MaPLe — DETERMINISM/disentanglement by purity, but CLOSED systems: no handlers, no effects, no host concurrency, and the schedule is compiler-chosen, not a user-installable swappable handler. Rayon/Cilk — STRUCTURED fork-join with provably efficient work-stealing, but race-freedom comes from a SEPARATE borrow checker (Rayon) or a DYNAMIC race detector (Cilksan), and the scheduler is fixed — no Seq|Thread|Simd|Gpu gradient, no !Thread capability. Structured concurrency (Trio/JEP/Senders) — structures control-flow LIFETIME but proves nothing about DATA races or capabilities inside the scope. OxCaml modes / à-la-Mode — the SOTA on STATIC data-race freedom, but it is a parallel axis-system grafted onto OCaml's types, not unified with an effect row or a parallel topology verb; modal effects under parallelism remain future work. Every one of them has the tentacle (separation, or determinism, or static safety, or structured lifetime, or accelerator reach) and none has the BODY: a single graph where the parallel topology, the schedule, the ownership proof, and the effect-negation are four projections of ONE verified read.

**Mentl's arm:** Mentl's parallel arm is the SPACE axis of the one cursor-read (PLAN §2, §5.U): one heap record FORKED as N branch thunks on a shared, lock-free-readable image, with per-thread bump arenas + inference-stable handles giving deterministic parallel codegen. It converges and surpasses each tentacle by collapsing the two disjoint lineages into one kernel: (1) The Halide separation is ABSORBED AND DEEPENED — the parallel TOPOLOGY is declared once by a verb (`<|` ref-borrows one shared input across N branches; `><` own-consumes N independent inputs — both fan out + tuple, merged at the substrate to ONE `PFanout` node carrying arity + an ownership aspect read from use-count, never a second node-kind), while the SCHEDULE is a `~> Schedule` HANDLER reading the live handler stack to pick `type Strategy = Seq | Thread | Simd | Gpu` (an ADT, never `mode==0/1/2`). Algorithm/schedule separation becomes a HANDLER-SWAP, and unlike Halide the verb stays PURE TOPOLOGY contributing zero effects and the schedule is a proved graph fact, not an untyped side-script. Mentl is the body: topology-verb + schedule-handler + ownership-proof + effect-negation as four projections of one graph, closed over any future scheduler/backend as just another `~>` handler (!Outside).
